# Cross-promo: мастер JSON

В `AMZN GoD → SDK Settings → Cross Promo → Config URL` можно указать один URL
мастер-файла для всех игр. При запуске SDK скачивает мастер, находит запись с
`PackageName`, совпадающим с `Application.identifier` текущей игры, и загружает
JSON с креативами по её `ConfigUrl`.

## Формат мастер-файла

```json
{
  "Packages": [
    {
      "PackageName": "com.example.gameone",
      "ConfigUrl": "https://cdn.example.com/cross-promo/gameone.json"
    },
    {
      "PackageName": "com.example.gametwo",
      "ConfigUrl": "https://cdn.example.com/cross-promo/gametwo.json"
    }
  ]
}
```

Готовый шаблон: [master.example.json](master.example.json). Замените примерные
package name и URL своими значениями перед размещением файла.

- Имена полей чувствительны к регистру: `Packages`, `PackageName`, `ConfigUrl`.
- `PackageName` — идентификатор самой игры, загружающей рекламу, из Player Settings.
  Это не `AppPackageName` рекламируемого приложения в JSON креативов.
- Для каждой игры должна быть ровно одна запись с точным совпадением package name.
  Несколько игр могут ссылаться на один JSON с креативами.
- `ConfigUrl` записи — полный URL по HTTP или HTTPS. Рекомендуется HTTPS.
- Поддерживается один уровень: мастер → JSON с креативами. Ссылки на другой
  мастер не поддерживаются.
- Мастер содержит `Packages`; конечный JSON — прежние `Weight` и `Videos`.
  Не объединяйте `Packages` и `Videos` в одном документе.

Прямой URL прежнего JSON с `Videos` также продолжает работать в том же
поле `Config URL`.

## Порядок видео через position

В каждом объекте `Videos` можно задать необязательное целое поле `position`
(именно в нижнем регистре). Нумерация начинается с **1**: `position: 3`
закрепляет видео на третьем месте повторяющейся очереди показов.
Свободные места заполняются креативами без закреплённой позиции по `Weight`.

Пример смешанной конфигурации:

```json
{
  "Weight": 1,
  "Videos": [
    {
      "Title": "Random A",
      "VideoUrl": "https://cdn.example.com/cross-promo/a.mp4",
      "Weight": 0.25
    },
    {
      "Title": "Fixed second",
      "VideoUrl": "https://cdn.example.com/cross-promo/b.mp4",
      "position": 2,
      "Weight": 0.5
    },
    {
      "Title": "Random C",
      "VideoUrl": "https://cdn.example.com/cross-promo/c.mp4",
      "Weight": 0.25
    }
  ]
}
```

Здесь первый и третий слоты заполняются `Random A` / `Random C` по весам,
а второй занимает `Fixed second`. Его вес не влияет на закреплённое место.
Для полностью заданного порядка укажите всем видео позиции `1`, `2`, …, `N`.

- Если положительного `position` нет ни у одного креатива, сохраняется прежний
  случайный выбор по весам и прежняя обработка кулдаунов.
- Отсутствующее поле, `0` и отрицательное значение означают отсутствие закрепления.
- Если позиция повторяется, её занимает первый креатив в массиве JSON;
  остальные участники с тем же номером заполняют свободные места по весам.
- Длина круга — максимум из исходного количества креативов и наибольшей позиции.
  После последнего слота очередь начинается с первого; новый загруженный конфиг
  начинает новую очередь. Счётчик очереди между запусками не сохраняется.
- Лимиты показов и фильтр установленных приложений продолжают действовать.
  Недоступный владелец освобождает свой слот; остальные позиции не перенумеровываются.
- Если в свободном слоте нет доступных незакреплённых креативов, пустые слоты
  пропускаются до ближайшего доступного закреплённого видео. Поэтому для строгого
  соответствия порядковому номеру каждого показа задавайте позиции без пропусков
  либо оставляйте доступные креативы для заполнения свободных мест.
- Закреплённые видео следуют очереди независимо от кулдауна. Для заполнения
  свободных мест кулдаун учитывается внутри незакреплённого пула и сбрасывается,
  когда этот пул исчерпан; повтор последнего видео избегается, если есть альтернатива.
- Предзагрузка не продвигает очередь. Слот расходуется в момент, когда SDK
  засчитывает показ: на первом кадре ExoPlayer, при запуске показа UnityVideoPlayer
  (существующая логика этого бэкенда).
- Явный показ через перегрузку с `PromoConfiguration` обходит очередь и не
  расходует её слот. Баннеры сохраняют прежнюю ротацию по порядку массива JSON.

Корневой `Weight` не меняется; `position` относится только к выбору видео
внутри cross-promo.

## Лимиты показов и AppLovin

Лимиты кросс-промо (`cap`, либо `MaxShowCount` в старых конфигах) применяются
только при включённом модуле AppLovin. Если модуль выключен в SDK Settings или
исключён из сборки, даже достигшие лимита креативы остаются доступны для показа
и предзагрузки.

При включённом AppLovin каждый вызов `ShowVideoPromo`, `ShowInterstitial` или
`ShowRewarded` сначала выбирает JSON-креатив с неизрасходованным лимитом. Когда
этот пул исчерпан, SDK пробует соответствующий формат MAX. Если в момент вызова
MAX не готов принять показ, SDK показывает JSON-креатив **сверх лимита** по тем же
правилам `position`, `Weight`, кулдауна и исключения установленных приложений /
собственной игры. Очередь JSON общая; фолбэк не начинает новый круг.

После исчерпания лимитов следующий JSON-креатив может предзагружаться для такого
фолбэка. При этом готовый MAX сохраняет приоритет на следующем запросе. Если нет
ни готового MAX, ни доступного JSON-креатива, вызывается `onClose` без показа.
`onRewarded` у JSON-фолбэка срабатывает по завершении видео, как при обычном
rewarded cross-promo. Асинхронная ошибка уже принятого MAX-показа не запускает
дополнительный JSON-показ.
Повторный запрос во время активного показа MAX также не запускает JSON-фолбэк.

Счётчики показов сохраняются и продолжают накапливаться. После повторного
включения AppLovin и перезапуска SDK лимиты снова учитывают накопленные показы.
Фильтры установленных приложений и собственной игры работают как прежде.
Правила кулдауна при использовании `position` описаны выше.

## Placement в событиях на бэкенд

События `cp_impression` и `cp_click` в `/v1/events` передают строковое поле
`placement` — формат кросс-промо, из которого произошёл показ или клик:

- `interstitial` — interstitial-видео;
- `rewarded` — rewarded-видео;
- `banner` — баннер.

Оба видеоплеера передают плейсмент показа и клика. Баннер передаёт `banner`
при каждом видимом показе и клике; условия отправки описаны ниже.
AppMetrica-событие `crosspromo_banner_click` также передаёт `placement="banner"`
(прежнее значение `banner_click` исправлено; имя события не изменилось).

Во всех штатных рекламных событиях дополнительно передаётся `ad_format`:
`interstitial`, `rewarded` или `banner`. Это общий формат для CrossPromo и MAX,
независимый от произвольных имён MAX placement. В текущих штатных событиях
CrossPromo значения `placement` и `ad_format` совпадают.

Пример payload клика:

```json
{
  "event_name": "cp_click",
  "event_id": "32d030b737ea4e589523bcbe6fef81a0",
  "paid_app_id": "com.example.promoted",
  "placement": "rewarded",
  "ad_format": "rewarded",
  "donor_app_id": "com.example.donor",
  "device_id_hash": "example-device-hash",
  "ts": 1790640000000
}
```

Для ручной отправки используйте перегрузки `TrackImpression`, `TrackClick`,
`TrackClickRoutine` с аргументом `placement` в `CrossPromoModule` /
`AnalyticsModule` либо соответствующие `TrackAnalytics*` в `AmznGoDSDKCore`.
Старые одноаргументные вызовы сохраняются; для них, а также для `null`, пустого
или состоящего из пробелов плейсмента поле не отправляется: источник неизвестен.
Для legacy-вызовов `ad_format` выводится только из точного известного значения
`placement`; для остальных значений формат не угадывается и поле пропускается.
Новые перегрузки с последним аргументом `adFormat` позволяют передать формат
явно через константы `AdAnalyticsFormat`. Неизвестный или неканонический формат
не сериализуется. Оба поля сохраняются в JSON очереди при повторной отправке.

Бэкенд должен принимать необязательное поле `ad_format` у `cp_*` и
`mediation_*`, сохраняя поддержку старых событий без него. Его схема и код
отсутствуют в SDK; приём нового поля необходимо проверить на стороне сервера.
Полный контракт, включая MAX-баннеры, описан в
[`Documentation~/README.md`](../../../Documentation~/README.md#advertising-event-fields).

Для установки требуется поддержка на бэкенде: после атрибуции по `device_id_hash`
и соответствию `paid_app_id` клика → `app_id` установленной игры установка должна
наследовать `placement` атрибутированного `cp_click`. При отсутствии плейсмента
в клике источник остаётся неизвестным. Код бэкенда отсутствует в SDK;
`free_first_open` / `paid_first_open` и ссылки Adjust здесь не меняются.

## Как переключить JSON без пересборки

1. Один раз обновите SDK в игре до версии с поддержкой мастера, задайте URL
   размещённого мастер-файла в `Config URL` и выпустите обновлённую сборку.
2. Разместите новый JSON с креативами по доступному URL.
3. Измените `ConfigUrl` нужной игры в мастер-файле, оставив URL самого мастера
   прежним. Опубликуйте обновлённый мастер.
4. При следующем запуске игры SDK прочитает мастер заново и загрузит новый JSON.
   Последующие переключения выполняются только на сервере.

Успешно загруженный конфиг действует до конца текущей сессии: периодического
опроса и переключения во время показа рекламы нет. Если начальная загрузка не
дала доступных креативов, сохраняются существующие фоновые повторные попытки SDK.

Настройте кеширование хостинга/CDN так, чтобы изменённый мастер был доступен на
следующем запуске: например, `Cache-Control: no-cache` с проверкой актуальности
или инвалидация кеша при публикации. Настройки CDN могут требовать отдельной
инвалидации. Конечный JSON тоже должен быть актуальным; при длительном TTL удобно
публиковать его по новому URL и менять ссылку в мастере.

## События баннера на бэкенде

При включённых Cross Promo и Analytics (с выбранным `App Type`, не `None`)
баннер отправляет в `POST /v1/events` события `cp_impression` и `cp_click`.
Оба содержат `placement: "banner"`; `paid_app_id` берётся из первого
`AppPackageName` креатива, а при его отсутствии — из `DefaultPromotedAppId`.
Без обоих идентификаторов событие не отправляется. URL и API key используются
из существующей конфигурации Analytics.

Показ фиксируется при назначении загруженного спрайта видимому баннеру и при
каждой ротации (раз в 8 секунд, включая повтор единственного креатива).
Скрытый баннер, выключенный `Image` и активный no-ads показы не создают.
Показы баннера в AppMetrica и Adjust не отправляются.

При клике SDK запускает отправку `cp_click` с `placement: "banner"` и отдельно
Adjust/TrackingUrl. Перед переходом в магазин общее ожидание ограничено
1,5 секунды; незавершённые запросы продолжаются на модуле после скрытия баннера.
После разрешения device ID готовый JSON сохраняется в существующей очереди
Analytics, поэтому при повторной отправке `placement` сохраняется.
Таймаут перехода не гарантирует доставку или запись в очередь за 1,5 секунды.

`first_open` отправляет установленная игра: она не знает плейсмент своего
источника установки. Для отчёта об установках бэкенд должен связать её
`app_id` с `paid_app_id` предшествующего cross-promo события по настоящему
`device_id_hash` и взять `placement` из этого события согласно своим правилам
атрибуции. Значение `unattributed` для такой связи не подходит. Серверная
атрибуция не реализуется SDK; клиентские `first_open`/`attribution` не меняются.

## Ошибки и диагностика

Если package name отсутствует или повторяется, URL неверен, JSON повреждён либо
конечный файл тоже является мастером, SDK сообщает причину в логах
`[CrossPromoConfig]`. Чужая запись вместо нужной игры не выбирается. При неудачной
загрузке возвращается пустой конфиг и действует существующий путь `no_fill` /
медиации и повторных попыток.

Меню `AMZN GoD → Debug → Cross-Promo Caps` также читает мастер по package name
текущего проекта и работает с конечным JSON с креативами.
